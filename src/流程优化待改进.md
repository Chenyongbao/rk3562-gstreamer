## 1. 模型版本管理

### 为什么重要

- 模型迭代时无法回滚 → 新模型线上出错只能改代码重编译
- OTA 下发无法确定"当前运行哪个版本"
- A/B 测试无法进行（同时跑两个版本对比效果）

### 当前状态

```
embedded_model.cpp  → 编译进二进制 → 无法单独更新
```

### 改进方案

```
/home/linaro/yolo_models/
├── v1.0.0/
│   ├── model.rknn
│   └── config.json       ← {"version":"1.0.0","input":[640,640],"classes":36,"mAP50":0.92}
├── v1.1.0/
│   ├── model.rknn
│   └── config.json       ← {"version":"1.1.0","input":[640,640],"classes":36,"mAP50":0.94}
├── current → v1.0.0/     ← 软链接，指向当前生效版本
├── previous → v1.0.0/    ← 软链接，指向上一版本（用于回滚）
├── candidate → v1.1.0/   ← 软链接，指向候选版本（用于灰度测试）
└── auto_rollback_flag     ← 空文件，启动时存在则回滚到 previous
```

### 启动逻辑（伪代码）

```
启动时:
  读取 current/config.json → 获取模型参数
  加载 current/model.rknn → rknn_init()
  验证首帧推理耗时正常
  若失败:
    检查 auto_rollback_flag 是否存在
    → 如果存在: 放弃本次，使用 previous/model.rknn
    → 如果不存在: 创建 auto_rollback_flag, 回退到 previous

版本切换:
  运维脚本: cp new.rknn candidate/model.rknn
  验证:        向设备发 PING → 设备尝试加载 candidate
  → 成功: ln -sf candidate current → 创建 previous 备份
  → 失败: rm candidate/model.rknn
```

### 投入估算

| 项目 | 代码量 | 难度 |
|------|--------|------|
| 模型目录结构 | 15 行 shell | 低 |
| config.json 解析 | 30 行 C++ (nlohmann/json) | 低 |
| 启动加载逻辑 | 50 行 C++ (修改 `InitRKNNCore`) | 低 |
| 回滚脚本 | 20 行 shell | 低 |
| **合计** | **~115 行** | **1 天** |

### 安全性考量

保留硬编码模型作为**终极保底**：

```cpp
// 启动优先级:
// 1. 尝试从文件系统加载 (current/model.rknn)
// 2. 如果不存在/校验失败 → 回退到硬编码模型
if (!loadFromFile("yolo_models/current/model.rknn")) {
    loadFromMemory(g_embedded_model_data, g_embedded_model_size);  // 保底
}
```

## 2. 数据流水线——训练闭环

### 为什么重要

- 模型在工厂 A 训练，在工厂 B 部署 → 场景漂移后精度下降
- 缺少反馈通道 → 不知道模型哪里识别错了
- 新物料类型无法及时加入训练集

### 当前状态

```
推理结果 → 一次性消费 → 无留存
```

### 改进方案——最简数据回流

```
生产设备 (RK3588)
    │
    │ 推理中 confidence < 0.3 的低置信度检测
    ▼
/home/linaro/low_conf/<timestamp>_<class>_<conf>.jpg
    │
    │ 每小时打包 (tar + 断点续传)
    ▼
云端训练服务器
    │
    │ 人工审核 / 自动标注 → 加入训练集
    │ 重训练 → 导出新 .rknn
    ▼
下发到生产设备 (见"端-云协同")
```

### 代码切入点

```cpp
// 在 yolo_wrapper.cpp 中，已有 confidence 信息
// 加这一段:
for (int i = 0; i < result->detection_count; i++) {
    if (result->detections[i].confidence < 0.3f && result->detections[i].confidence > 0.0f) {
        char fname[256];
        snprintf(fname, sizeof(fname),
                "/home/linaro/low_conf/%llu_%d_%.3f.jpg",
                (unsigned long long)frame_id,
                result->detections[i].class_id,
                result->detections[i].confidence);
        cv::imwrite(fname, bgr);
    }
}
```

### 投入估算

| 项目 | 代码量 | 难度 |
|------|--------|------|
| 低置信度保存 | 10 行 | 低 |
| 打包上传脚本 | 20 行 shell (tar + scp/curl) | 低 |
| 服务器接收端 | 用 Flask 写 50 行 Python | 低 |
| 训练脚本 | 复用 rknn_model_zoo 的 convert.py | 已有 |

## 3. 可观测性与监控

### 为什么重要

- 设备部署在产线 → 看不到运行状态 → 出问题只能去现场
- 推理延迟突变 → 不知道是 NPU 降频还是输入尺寸变了
- 产线有 10 台设备 → 哪台在报错？哪台负载高？

### 当前状态

```cpp
// yolo_wrapper.cpp 已有的日志:
fprintf(stderr, "[YOLO] frame=12345 det=2 pre=3.2ms inf=45.1ms post=8.7ms total=57.0ms\n");
// → 仅输出到终端，不结构化，不持久化
```

### 改进方案

#### 3.1 轻量方案（不引入 Prometheus）

```cpp
struct RuntimeMetrics {
    std::atomic<uint64_t> total_frames{0};
    std::atomic<uint64_t> total_detections{0};
    std::atomic<uint64_t> error_frames{0};
    double latency_buffer[100];  // 滑动窗口
    int    latency_index{0};
};

// 在 yolo_detect_nv12 中:
metrics.total_frames++;
metrics.total_detections += result->detection_count;
metrics.latency_buffer[metrics.latency_index++ % 100] = timing.totalMs;

// 在 HTTP server 中暴露:
// GET /metrics → 返回 JSON
{
  "total_frames": 12345,
  "total_detections": 5678,
  "avg_latency_ms": 52.3,
  "p99_latency_ms": 78.1,
  "fps": 19.2,
  "error_rate": 0.001
}
```

#### 3.2 标准方案（引入 Prometheus）

```cpp
#include <prometheus/counter.h>
#include <prometheus/histogram.h>

// 三个核心指标:
Counter    yolo_frames_total      // 累计帧数
Counter    yolo_detections_total  // 累计检测数
Histogram  yolo_latency_ms        // 推理延迟分布 (自动算 p50/p90/p99)
```

**使用 prometheus-cpp 库**：https://github.com/jupp0r/prometheus-cpp

### Dashboard 参考

| 面板 | 指标 |
|------|------|
| 推理延迟 | `histogram_quantile(0.99, yolo_latency_ms)` |
| 帧率 | `rate(yolo_frames_total[1m])` |
| 检测密度 | `rate(yolo_detections_total[1m]) / rate(yolo_frames_total[1m])` |
| 错误率 | `rate(yolo_error_frames_total[1m])` |

### 投入估算

| 方案 | 代码量 | 难度 | 适用场景 |
|------|--------|------|---------|
| 轻量 JSON | 80 行 C++ | 低 | 单机调试 |
| Prometheus 标准 | 60 行 C++ + docker-compose | 中 | 多机产线 |
| Grafana Dashboard | JSON 配置 (可导入模板) | 低 | 可视化 |

## 4. 端-云协同

### 为什么重要

- 模型迭代后需手动 USB 烧写 → 10 台设备 = 10 次操作
- 无 OTA 能力 → 无法远程管理分布式设备

### 改进方案——基于 HTTP 的模型下发

```
┌──────────────────────────┐       ┌──────────────────────┐
│ 云端 (x86 服务器)         │       │ 边缘设备 (RK3588 ×N)  │
│                          │       │                      │
│ /models/latest/          │ HTTP  │ 每 5 分钟:            │
│   model.rknn             │◄─────┤   GET /version.json   │
│   config.json            │       │   → 比较本地版本      │
│   version.json           │       │   → 如不一致:          │
│   checksum.md5           │       │   GET /model.rknn     │
│                          │       │   → 保存到 candidate/ │
│                          │       │   → 验证后切换 current │
└──────────────────────────┘       └──────────────────────┘
```

### 接口定义

```json
// GET /api/v1/models/yolo/version
Response:
{
  "model": "yolo_seg",
  "version": "1.2.0",
  "md5": "a1b2c3d4e5f6...",
  "release_date": "2026-06-20",
  "min_rknn_version": "2.0.0",
  "force_update": false
}
```

### 安全机制

```
1. 下载后校验 MD5 → 不匹配则丢弃
2. 加载后跑 3 帧预热推理 → 延迟正常才切换
3. 失败自动回滚到 previous
4. 硬编码模型作为最终保底
```

### 参考项目

[KubeEdge Sedna](https://github.com/kubeedge/sedna) — 华为开源，全中文文档。

## 5. 模型加密与IP保护

### 为什么重要

- 模型文件可被 dd/cat 直接拷贝出去
- 竞争对手拿到 .rknn 文件 → 反编译或直接在另一台设备跑
- 训练成本数十万的模型 → 无保护等于白做

### 当前状态

```
embedded_model.cpp → 编译进 ELF 二进制 → strip 后无符号表
→ 优势: 对外行有混淆效果
→ 弱点: 专业人士可用 binwalk 或直接 strings 定位模型头 (RKNN magic: 0x524B4E4E)
```

### 改进方案——分层防御

| 层级 | 措施 | 实施难度 | 防护等级 |
|------|------|---------|---------|
| L0 | 模型文件权限 600 (仅 root 可读) | 1 行 chmod | 低 |
| L1 (已有) | 编译进二进制 + strip 符号表 | 已完成 | 中低 |
| L2 | AES-256 加密模型文件，密钥存 eFuse/OTP | 80 行 C++ (OpenSSL) | 中高 |
| L3 | RK3588 TrustZone (OPTEE) 中执行解密和推理 | 需瑞芯微 SDK 支持 | 高 |

### L2 实现参考

```cpp
// 存储: 模型文件用 AES-256-GCM 加密
// openssl enc -aes-256-gcm -in model.rknn -out model.rknn.enc -K <hex_key>

// 加载:
uint8_t key[32];
readKeyFromEFuse(key);  // 从芯片 OTP 读取唯一密钥

uint8_t* encrypted = readFile("model.rknn.enc");
uint8_t* decrypted = AES_GCM_decrypt(encrypted, key);

rknn_init(&ctx, decrypted, size, ...);
secure_zero(decrypted);  // 解密后立即从内存中擦除
```

### 芯片唯一 ID 绑定

RK3588 有 `chip_uid`（OTP 区域，不可更改），可绑定模型到特定设备：

```cpp
// 模型文件中嵌入允许的 chip_uid 列表
// 运行时:
if (model.chip_uids.find(getChipUID()) == model.chip_uids.end()) {
    return ERROR_MODEL_NOT_AUTHORIZED;
}
```

## 6. 模型服务与API化

### 为什么重要

- 现有 TCP 协议私有的 → 外部系统无法对接
- 产线 MES/ERP 系统通常走 REST API
- 标准化的好处：任何语言都能调用、有 Swagger 文档、可做 API 网关限流

### 当前状态

```
TCP 9999 → 二进制协议 → DETECT 命令 → JSON+JPEG 响应
→ 优点: 性能高，延迟低
→ 缺点: 非标准，无法对接外部系统
```

### 改进方案

在现有 TCP server 之外，增加一个 HTTP 端点（并存）：

```
设备启动:
  TCP 9999 → 二进制协议 (内部高性能通道，不动)
  HTTP 8080 → REST API (外部对接通道，新增)
```

### HTTP API 设计

```
POST /api/v1/detect
  Content-Type: multipart/form-data
  Body: image=<jpeg>
  Response: {
    "objects": [
      {"class_id": 5, "class_name": "cherry_wood", "confidence": 0.89,
       "bbox": [100,200,50,80], "polygon": [[100,200],[150,200],...]}
    ],
    "inference_ms": 52.3,
    "model_version": "1.0.0"
  }

GET  /api/v1/health
  Response: {"status":"ok","model_version":"1.0.0","uptime_sec":86400}

GET  /api/v1/metrics        (Prometheus 格式)
```

### 代码实现

使用 [cpp-httplib](https://github.com/yhirose/cpp-httplib)（单头文件，零依赖）：

```cpp
#include "httplib.h"

httplib::Server srv;
srv.Post("/api/v1/detect", [&](const httplib::Request& req, httplib::Response& res) {
    // 1. 解码 JPEG
    // 2. 调用 model.inference()
    // 3. 构造 JSON 响应
    res.set_content(json_str, "application/json");
});
srv.listen("0.0.0.0", 8080);
```

### 投入估算

| 项目 | 代码量 | 难度 |
|------|--------|------|
| cpp-httplib 头文件 | 0 (拖入项目) | 无需编译 |
| HTTP server 启动 | 10 行 | 低 |
| /health 端点 | 15 行 | 低 |
| /detect 端点 | 40 行 | 低 |
| /metrics 端点 | 30 行 | 低 |
| **合计** | **~100 行** | **半天** |
