> 命令层单线程串行执行，归位用 `homing_mutex_` 互斥保护，无并发仲裁层。**

## 钉死的地基（任何答案的前提）

1. **共享设备的"客户"是代码里的内部调用者，不是 TCP 客户端。** 一台 Klipper 有 9 个内部调用者都通过 `IKlipperDevice*` 访问它：DETECT、CALIB、测厚、焦距标定、总高、XY 偏移、副摄标定、RTSP 线程、共享辅助函数。
2. **执行模型是"同步分组串行"**：DETECT 是一组步骤（唤醒→归位→测厚→移动→两帧检测），CALIB 是一组步骤，各自在命令线程里一次性跑完。
3. **互斥策略只有一种：忙就拒绝（回 `KLIPPER_BUSY`），不阻塞、不排队。**
4. 命令层单线程串行，但存在真实的跨线程调用：RTSP 线程发 G4、CALIB 里 `std::async` 副摄线程。

## 第一档：设计决策（必考）

### Q1. 为什么"忙就拒绝"，而不是让第二个调用者阻塞等待？

**答**：设备操作是秒级的（归位 5 分钟、标定几分钟）。如果阻塞等，调用线程会被占死几分钟；而业务上"标定没结束你来 DETECT"本就应该立即失败，让上层决定重试还是放弃。所以入口是一个**非阻塞的原子尝试**（`compare_exchange_strong`，忙则返回 false），拿到 `KLIPPER_BUSY` 就返回。这等价于 `std::mutex::try_lock` 与 `lock` 的区别：锁是阻塞等，这里是立即失败的申请制。

### Q2. 为什么不用一把全局 mutex 就完事？

**答**：三个原因：
1. mutex 阻塞，秒级持有会白占线程；
2. mutex 只防"并发"，不防"语义冲突"——G4 唤醒和 DETECT 的 G1 同时发、互不冲突，mutex 会把它们不必要地串行化；而我按"是否冲突"分类，只拦真正会冲突的命令；
3. mutex 不带"设备现在在忙什么"的信息。

### Q3. 一个裸的 `atomic<bool>` 忙标志不够吗，为什么还要状态机？

**答**：忙标志只能回答"忙不忙"，`DeviceStateMachine` 能回答"**在忙什么**"（Detecting / Calibrating）。价值是可观测性：状态回报给上层、日志定位时知道设备卡在哪个流程，也为将来"Detecting 时拒绝 CALIB"这类按状态仲裁留了空间。成本只是一个 `atomic<DeviceState>` 枚举。

### Q4. 为什么把 forceHome 拆成一串有名字的步骤（KlipperJob）？

**答**：三个收益：
1. 步骤有名字，失败时错误信息能精确到"卡在 G28 这步"，而不是一个模糊的大失败；
2. 失败处理统一收敛在 `run()` 里，不用每个业务函数重复 `if (!xxx) return`；
3. 将来要加取消、进度，只需在 `run()` 里加钩子，不改任何业务函数。这个思路参考了 Klipper 固件自己的命令处理——命令是"小的、排队的"。

### Q5. 为什么业务层依赖 `IKlipperDevice` 接口，而不是直接用 `KlipperManager`？

**答**：
1. 可 mock：测试可以用假实现，不碰真硬件；
2. 可替换：模拟器、协议升级都只需换实现，上层不动；
3. 依赖方向清晰：handler/service → 接口 ← 实现；
4. 全库只有组合根（`app_runtime.cpp`）创建 `KlipperManager` 单例，业务服务一律拿接口指针，杜绝到处 `instance()`。

### Q6. 为什么有的命令要互斥、有的不用？（控制/唤醒/只读三类）

**答**：判别标准不是"是否碰设备"，而是"**是否会与其他操作冲突**"：
- **会改状态、可能冲突的**（G1/G28/激光/下探）：必须先进互斥，拿不到就拒绝；
- **不改状态的唤醒类**（G4 唤醒、灯、蜂鸣）：免互斥。因为 G4 是唤醒：机器有功耗休眠，休眠停掉 Klipper 并丢失状态，固件没有专用唤醒指令，就用最轻量的 `g4 p20` 占位。它只在休眠态有效，而休眠态下不可能有别的操作在跑；清醒态下是 no-op。所以它天然不冲突；
- **纯查询的**（queryLaserDistance/queryFocal）：免互斥，只读。

保守原则写死在接口注释里：不确定一条命令会不会冲突，就进互斥。

## 第二档：深挖挑刺（送命题）

### Q7. 命令层单线程，互斥标志在命令之间根本不会触发——这套东西是不是自欺欺人？

**答**：不是。它防的是**跨线程**调用：RTSP 线程会发 gcode、CALIB 里有 `std::async` 副摄线程，都是真实的非命令线程。只是当前它们要么走免互斥的唤醒路径（RTSP 只发 G4），要么被 `future.get()` 自我串行化（副摄线程）。所以今天确实"没被逼到墙角"，但它的存在保证了"**一个逻辑操作独占设备**"这个不变量在所有线程面前都成立。我会主动说明：它的完整价值要等内部调用者真正并发时才兑现，现在是防御性设计。

### Q8. CALIB 里 `std::async` 副摄线程和主线程都在用 Klipper，这不是并发吗？互斥怎么保证？

**答**：互斥保证的是"CALIB 这一整个操作"与"其他操作"互斥，**不保证 CALIB 内部线程之间互斥**。副摄线程不重新申请互斥，它被视为同一个逻辑操作的一部分；主线程在 `future.get()` 处阻塞，副摄跑完才继续，所以任一时刻实际只有一条线程在驱动硬件。这是 **CALIB 自身结构（顺序调用 + future 同步）保证的，不是互斥标志保证的**——如果哪天 CALIB 内部两条线程同时碰 Klipper，互斥标志发现不了。这是设计边界，我认。

### Q9. RTSP 线程发 G4 时 DETECT 可能在跑 G1，两个 HTTP 请求同时打到 Klipper，安全吗？

**答**：分两层。传输层：每次请求都是独立创建的 curl 句柄，互不干扰，并发 POST 本身安全。语义层：G4 是 no-op 唤醒，和 G1 不冲突，这正是它免互斥的底气。**但如果 RTSP 发的是 G1 就会和 DETECT 踩轴**——所以会冲突的命令必须走互斥，这靠的是代码约定和评审，不是编译器强制。

### Q10. 被拒绝的调用者怎么办？只有拒绝没有排队，撞上了怎么处理？

**答**：申请失败返回 false → 调用方直接回 `KLIPPER_BUSY`，由上层决定重试或放弃。这是纯拒绝策略的自然结果：**没有自动重试、没有排队**。对秒级独占设备，"立即失败 + 上层重试"比"静默排队"更可预期，也不会堆积任务。

### Q11. 如果固件改了，G4 不再是唤醒语义（比如固件支持了真正的唤醒命令），你的设计哪里会受影响？

**答**：不会崩，但"唤醒免互斥"的**前提**会失效。`sendG4Wait` 集中在 `klipper_flow.cpp` 一处，换实现只改一处；但前提变了要重新审计"G4 是否还天然不冲突"。所以唤醒类命令只保留 G4/灯/蜂鸣这几个明确不改状态的，且接口注释里写明保守原则"不确定就进互斥"。

## 第三档：可靠性与边界

### Q12. 拿到互斥后崩溃/泄漏了没释放，设备会不会永久 busy？

**答**：进程崩溃：整个进程退出，标志随进程消失，重启即恢复。异常和提前 return：RAII 守卫（`KlipperExclusiveGuard`）在析构里自动释放，构造在栈上、禁拷贝、必然析构，所以正常路径不会漏。真实的缺口是：**没有超时/看门狗**——如果守卫被堆分配且不析构、或线程被强制 abort，标志会卡在 busy。状态机的 `Error` 状态就是留给"需要人工介入"的未来场景，现在没启用。

### Q13. forceHome 失败、DETECT 中途失败，机器停在危险位置怎么办？

**答**：双保险。`KlipperExclusiveGuard` 保证"释放互斥"（不会 busy 死锁）；`FinalHomeGuard`（armed）保证"回到安全位"——任何提前 return 都在析构时补发 `G90/G28/M400`。**一个不对称点，主动说**：DETECT 用 `FinalHomeGuard` 自动兜底；CALIB 是靠各出口显式调 `runFinalHoming`，后者更依赖人工不遗漏。

## 第四档：演进与格局

### Q14. 如果要支持"取消标定"，你的设计怎么做？

**答**：协作式取消：加一个共享的 `atomic<bool> cancel_requested`，在 KlipperJob 的步骤之间检查，为 true 就返回。因为步骤已经拆好，检查点天然存在；配合 RAII，取消后自动回到安全位。纯同步串行就能做，不需要改执行模型。

### Q15. 你的实现和 Klipper 固件自己的命令处理有什么异同？

**答**：Klipper 固件 `gcode.py` 里 `run_script` 是 `with self.mutex:` 串行执行一串 gcode——它选的是"排队串行"，因为它在真驱动电机，必须在单线程里串行。我这一层是业务编排，秒级操作多，选"拒绝"更合适。两个层次、两种策略，都成立：固件管实时，我管编排。

### Q16. 和 ROS2 的 ros2_control 框架对比呢？

**答**：思路一致：一个中心组件统一管理独占设备接口，调用方申请使用、作用域结束自动归还，RAII 思想相同。差异：ros2_control 是完整框架（硬件生命周期管理 + 实时控制循环 + 插件加载），我的 `KlipperManager` 只做了"仲裁 + HTTP 传输"这一薄层——Klipper 硬件的实时控制本身在固件（Klipper/Moonraker）里，我只是客户端。我复用了一个更成熟的分层。

## 附：主动交代的弱点清单（比被问出来强十倍）

1. 互斥仲裁当前在命令层不触发（单线程串行），是防御性设计。
2. 互斥没有超时/看门狗，极端情况下可能卡 busy。
3. CALIB 内部线程互斥靠自身结构保证，不靠互斥标志。
4. CALIB 归位靠显式调用、DETECT 靠 RAII 兜底，两处不对称。
5. "哪些命令要互斥"是代码约定 + 评审维持的，不是编译器强制。
6. 只有拒绝没有排队，被拒绝方无自动重试。

## 总括话术（收尾用）

> "这台机器只有一台 Klipper，却被 9 个内部调用者共享。我把它做成：一个接口 `IKlipperDevice` 做唯一入口，一个实现 `KlipperManager` 管所有通信；用一个原子忙标志 + 状态机做'忙就拒绝'的互斥仲裁，RAII 守卫保证任何路径都能释放；长操作拆成有名字的小步骤，fail-fast；执行是同步分组串行的。仲裁按'会不会冲突'分三类：会改状态的必须互斥，G4 唤醒和纯查询免互斥——因为 G4 只在休眠态生效，天然没有竞争对手。整个设计不依赖 TCP 连接模型，它防的是跨线程调用和未来的内部并发。"
