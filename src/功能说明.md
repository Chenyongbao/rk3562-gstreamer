# t3/reset/src 功能说明

## 1. 代码整体定位

`t3/reset/src` 对应的是一个运行在 RK3562 平台上的视觉服务程序，编译目标为 `bin/reallinkCVserver`。它不是单一功能模块，而是一套把“采集、俯视图生成、RTSP 推流、目标检测、设备联动、相机标定”串起来的完整应用。

从代码实现看，这套程序的核心职责有 6 类：

1. 从主摄像头采集高分辨率 NV12 图像。
2. 输出两路 RTSP 视频流：
   - 原始缩放流 `stream_original`
   - 俯视图流 `stream_bev`
3. 通过统一 TCP 指令服务提供 `PING / DETECT / CALIB` 等控制能力。
4. 基于内嵌 RKNN YOLO 模型执行检测，并返回 JSON + JPEG 结果。
5. 通过 Klipper/Moonraker 控制机械运动、激光测距、补光灯等外设。
6. 完成主摄、副摄、XY 偏移、总高等标定，并把结果回写到配置文件和二进制标定文件。

## 2. 程序启动与主流程

### 2.1 入口

- 文件：`main.cpp`
- 功能：
  - 打印版本号 `REALLINKCV_VERSION`
  - 注册 `SIGINT / SIGTERM`
  - 创建 `AppRuntime`
  - 调用 `AppRuntime::run()`

### 2.2 AppRuntime 负责的事情

- 文件：`app/app_runtime.h`、`app/app_runtime.cpp`
- 作用：把整个程序拆成“初始化 -> 运行 -> 清理”三个阶段。

启动时依次完成：

1. `initCoreServices()`
   - 初始化 `libcurl`
   - 初始化 `KlipperManager`
   - 初始化 `RGA`
2. `initMediaPipeline()`
   - 启动双路 RTSP 服务
   - 初始化主摄最新帧缓存与 BEV 最新帧缓存
   - 打开 V4L2 摄像头 `/dev/video11`
   - 初始化原图队列、BEV 队列
   - 绑定两个工作线程上下文
3. `initCommandServer()`
   - 初始化 YOLO（失败时程序继续运行，但 `DETECT` 功能会被关闭）
   - 启动统一 Socket 服务
   - 注册命令处理器
4. `startStreamWorkers(app_)`
   - 启动原图推流线程
   - 启动 BEV 推流线程
5. `runCaptureLoop(app_, running_flag_)`
   - 进入采集主循环

退出时统一调用 `shutdownApp()`，按逆序释放队列、相机、RTSP、YOLO、RGA、Klipper、curl 等资源。

## 3. 视频链路与数据流

### 3.1 输入源

- 文件：`video/v4l2_capture.h`、`video/v4l2_capture.cpp`
- 主摄输入配置来自 `config.h`
  - 设备：`/dev/video11`
  - 分辨率：`4224 x 3136`
  - 像素格式：`NV12`
  - Buffer 数量：`6`

这个模块负责：

- 以 V4L2 MMAP 方式申请缓冲区
- 尝试把每个 V4L2 buffer 导出成 DMA-BUF fd
- 启动采集流
- 提供 `dequeue / queue`

如果 DMA-BUF 导出成功，就能走零拷贝链路；否则部分功能退化为内存拷贝路径。

### 3.2 采集主循环

- 文件：`app/capture_loop.cpp`

采集线程做的事情是：

1. 从 V4L2 取一帧。
2. 检查是否存在原图客户端、BEV 客户端、BEV 强制刷新请求、主摄 fresh-copy 请求。
3. 把当前帧封装为 `VideoFrameDesc` 并交给 `VideoRouter` 分发。
4. `VideoRouter` 按已注册消费者分别投递：
   - `OriginalRtspConsumer`
   - `BevRtspConsumer`
   - `MainCameraLatestFrameConsumer`
5. 如果没有任何客户端，也没有待处理的 refresh 请求，则直接归还当前 V4L2 buffer。
6. 分发结束后立即 `QBUF` 归还当前 V4L2 buffer，不再等待任何下游 worker 释放。
7. 每 10 秒打印一次统计信息

这里有一个很关键的实现特性：

- 主摄 latest frame 不再由主循环直接更新，而是由 `MainCameraLatestFrameConsumer` 在存在 fresh-copy 请求时更新。
- BEV latest frame 不再由采集线程维护，而是在 BEV 输出路径完成后发布到兼容缓存。
- 因此 `DETECT`、标定、焦距、偏移等旧接口仍可通过 latest-frame 兼容层取帧，但底层来源已经与主采集循环解耦。

### 3.3 帧队列

- 文件：`core/frame_queue.h`、`core/frame_queue.cpp`

程序内部仍保留两个固定长度队列，主要作为现有 worker 的过渡承接层：

- `original_queue`
- `bev_queue`

特点：

- 队列长度固定为 `32`
- 队列满时丢弃最旧帧，而不是阻塞主采集线程
- 对 DMA-BUF 帧，仅通过 `release callback` 回收消费者私有 dmabuf，不再承接 V4L2 source buffer 生命周期
- 支持 `shutdown`，方便线程安全退出

这个设计的目标是“优先保证实时性，不追求每帧必达”。

### 3.4 最新帧缓存

- 文件：`video/LatestNv12FrameBuffer.h`、`video/LatestNv12FrameBuffer.cpp`

代码维护了两份线程安全的最新帧缓存：

1. 主摄最新帧缓存
2. BEV 最新帧缓存

用途：

- 主摄缓存：供主摄标定、截图类流程使用
- BEV 缓存：供 `DETECT` 命令读取

支持：

- `copy()`：直接复制当前最新帧
- `copy_newer_than()`：等待比某个 `frame_id` 更“新”的一帧，`DETECT` 第二次抓图就用到了这个能力

## 4. RTSP 推流功能

### 4.1 双路 RTSP 服务

- 文件：`rtsp/dual_rtsp_server.h`、`rtsp/dual_rtsp_server.cpp`

程序启动后会创建两个 RTSP 输出：

- 原图流：`rtsp://192.168.50.1:8554/stream_original`
- 俯视图流：`rtsp://192.168.50.1:8554/stream_bev`

对应职责：

- 创建 GStreamer RTSP Server
- 为两路流各自创建 `appsrc -> encoder -> rtph264pay` 管线
- 在 RTSP 侧维护全局递增 `frame_idx`
- 初始化 BEV 处理器

### 4.2 RTSPStreamer

- 文件：`rtsp/rtsp_streamer.h`、`rtsp/rtsp_streamer.cpp`

该模块负责把图像帧真正送进 GStreamer 的 `appsrc`。

支持两种推送方式：

1. 普通内存帧推送
2. DMA-BUF 推送

当前实际运行中以 DMA-BUF 路径为主。

它还负责：

- 仅在 `appsrc` 进入 `PLAYING` 状态时推帧
- 依据 `need-data / enough-data` 做背压控制
- 背压时跳帧计数，不阻塞整条链路
- 给每一帧设置 PTS/DTS

### 4.3 原图推流线程

- 文件：`app/stream_workers.cpp`

`original_worker_thread()` 的职责：

1. 从 `original_queue` 取出由 `OriginalRtspConsumer` 投递的私有 DMA-BUF 帧
2. 如果需要，继续做 RTSP 推流侧缩放/推送
3. 把结果以 DMA-BUF 形式送进原图 RTSP 流

特点：

- 只接受 DMA-BUF 帧
- 非 DMA-BUF 原图会被丢弃并记录告警
- 使用一个小型 DMA-BUF 池做循环复用，减少反复分配

### 4.4 BEV 推流线程

- 文件：`app/stream_workers.cpp`

`bev_worker_thread()` 的职责：

1. 从 `bev_queue` 取出由 `BevRtspConsumer` 投递的私有输入帧
2. 在本线程绑定 OpenGL/EGL 上下文
3. 调用 `bev_process_frame()` 把主摄图像转换成俯视图
4. 通过 `BevLatestFrameUpdater` 更新 BEV latest frame 兼容缓存
5. 从 BEV 处理器取出输出 DMA-BUF
6. 推送到 BEV RTSP 流

特点：

- 当前实现要求 BEV 输出走 DMA-BUF 推流
- 如果流不是 DMA-BUF 模式，则该帧会被直接丢弃

### 4.5 RGA 与 DMA-BUF 工具

- 文件：`rtsp/rga_processor.*`
- 文件：`core/dmabuf_utils.*`

作用：

- `RGA` 负责 NV12 图像缩放
- `dmabuf_utils` 负责从 `/dev/dma_heap/system` 申请和释放 DMA-BUF

它们共同支撑原图零拷贝缩放推流链路。

## 5. BEV 俯视图功能

### 5.1 处理入口

- 文件：`reallink_ogles/bev_api.h`、`reallink_ogles/bev_api.cpp`

BEV 模块基于 OpenGL ES / EGL 实现，核心流程是：

1. `cameraInit()` 读取当前标定参数
2. 生成俯视图 remap map
3. 初始化 EGL、Shader、贴图、帧缓冲
4. 每帧执行纹理上传 + remap 渲染 + 输出读取

### 5.2 标定参数热更新

`bev_process_frame()` 在运行时会检查 map version。

这意味着：

- 当标定结果或 XY offset 更新后
- BEV 处理器可以自动重新装载 map texture
- 新的俯视图映射会生效

这是 `CALIB` 和 `XYoffset` 能影响在线 BEV 结果的关键机制。

### 5.3 reallink_ogles 目录职责

`reallink_ogles` 目录除了 `bev_api.*` 外，还包含：

- `camera.*`：相机模型、俯视映射相关逻辑
- `gles_*.*`：OpenGL 初始化、纹理、shader、渲染
- `dma_buffer.*`：图形侧 DMA-BUF 交互
- `file_utils.*`：`reallinkCV.conf` 读写

整体上这是“俯视图生成 + 配置持久化”的底层支撑目录。

## 6. 统一命令服务

### 6.1 服务概况

- 文件：`protocol/UnifiedSocketServer.h`、`protocol/UnifiedSocketServer.cpp`

程序会在 `192.168.50.1:9999` 启动统一 TCP 服务。

职责：

- 接收客户端连接
- 自动识别文本协议或二进制协议
- 解析命令
- 把命令交给 `CommandRouter`
- 返回统一的二进制响应

注意：

- 服务端当前是同步处理连接的
- `accept()` 到一个客户端后，会在同一个线程内循环处理该连接
- 也就是说当前不是“每个客户端一个线程”的并发服务器模型

### 6.2 支持的请求协议

#### 文本协议

- 客户端直接发送一行命令
- 以 `\n` 或 `\r\n` 结束
- 例如：`PING`

#### 二进制协议

- 前 4 字节是网络字节序的命令长度
- 后面紧跟命令内容

服务端会通过前几个字节判断是否为二进制命令。

### 6.3 响应格式

所有响应最终都走 `sendBinaryResponse()`，格式为：

1. 4 字节 `total_len`
2. 4 字节 `json_len`
3. JSON 文本
4. 可选 JPEG 数据

因此即使客户端用文本协议发命令，收到的也仍是二进制响应包。

### 6.4 路由

- 文件：`protocol/CommandRouter.h`

路由器职责：

- 按命令名找到对应 handler
- 对所有 `CALIB*` 命令做前缀路由

也就是说：

- `CALIB`
- `CALIB-0`
- `CALIB-1`

都会进入同一个 `CalibCommandHandler`，再由 handler 内部细分流程。

## 7. 各命令功能说明

### 7.1 PING

- 文件：`handlers/PingCommandHandler.h`
- 功能：心跳测试
- 返回：`{"status":"PONG"}`

### 7.2 DETECT

- 文件：`handlers/DetectCommandHandler.cpp`

`DETECT` 是一条业务链很长的命令，主要流程如下：

1. 确保 `KlipperManager` 已初始化。
2. 执行 `ensureHomed()`，保证设备已归位。
3. 从 BEV latest frame 读取一帧 NV12 图像。
4. 调用 YOLO 执行第一次检测。
5. 基于第一次检测结果进入 thickness 流程。
6. 控制机械移动到固定点位 `X50 Y50 Z0`。
7. 等待比第一帧更新的 BEV 帧。
8. 对第二帧再次执行 YOLO。
9. 从 Moonraker 查询 `focal_long / focal_short`。
10. 从 `/home/linaro/reallinkCV.conf` 读取 `TotalHigh`。
11. 生成 JSON 结果。
12. 尝试把第二帧编码成 JPEG。
13. 通过统一响应格式把 JSON + JPEG 返回给客户端。
14. 最后执行一次 `forceHome()`。

返回 JSON 中包含的主要内容：

- 图像宽高
- 目标数量
- `focal_long / focal_short`
- `TotalHigh`
- `thickness` 子结构
- `objects` 检测结果数组

#### DETECT 的依赖条件

1. YOLO 初始化必须成功，否则 `DETECT` handler 根本不会注册。
2. BEV latest frame 必须存在，否则返回 `NO_BEV_FRAME`。
3. Moonraker / Klipper 必须可用，否则归位和移动无法执行。

#### thickness 功能

- 文件：`yolodetect/thickness.h`、`yolodetect/thickness.cpp`

它在 `DETECT` 中承担的职责是：

1. 从 YOLO 结果里选一个目标框
2. 计算目标中心点
3. 把像素坐标换算成运动平台 XY 坐标
4. 控制平台移动
5. 执行 Z 轴下探 + 激光测距
6. 结合 `totalHigh` 计算厚度补偿
7. 更新 BEV 运行时厚度补偿状态

因此 `DETECT` 不只是“看图识别”，它还会联动机械执行一次测高流程。

### 7.3 CALIB / CALIB-0

- 文件：`handlers/CalibCommandHandler.cpp`

`CALIB`（以及效果相同的 `CALIB-0`）用于执行完整标定链路。

主要步骤：

1. 初始化 KlipperManager。
2. 创建本次标定 session 目录。
3. 执行归位。
4. 从主摄 latest frame 读取一帧，做主摄鱼眼标定。
5. 主摄失败时最多重试 3 次。
6. 主摄成功后，执行 `XYoffset` 标定。
7. 把 XYoffset 结果换算成副摄激光参考点。
8. 启动副摄标定。
9. 成功后写回 `reallinkCV.conf`。
10. 调用 `cameraInit()` 重新加载相机参数。
11. 返回 `{"status":"SUCCESS"}`
12. 最终执行一次归位。

### 7.4 CALIB-1

`CALIB-1` 是“只测总高”的快捷命令。

流程：

1. 归位
2. Z 轴逐步下降
3. 通过激光测距得到有效值
4. 计算 `totalHigh`
5. 写入配置文件和标定 bin
6. 返回 `{"TotalHigh":xxx}`

### 7.5 QUIT 的实际状态

`CommandRouter` 的未知命令提示里写了：

- `PING`
- `DETECT`
- `CALIB`
- `CALIB-0`
- `CALIB-1`
- `QUIT`

但当前代码里并没有注册 `QUIT` 的 handler，因此它不是一个已经实现完成的功能点。

## 8. YOLO 检测功能

### 8.1 对外封装

- 文件：`yolodetect/yolo_wrapper.h`、`yolodetect/yolo_wrapper.cpp`

这个模块提供：

- `yolo_init()`
- `yolo_detect_nv12()`
- `yolo_get_last_objects_json()`
- `yolo_cleanup()`

输入是 NV12 图像，内部会先转 BGR，再送给 RKNN 模型推理。

### 8.2 模型实现

- 文件：`yolo/YOLOSegmentor.h`、`yolo/YOLOSegmentor.cpp`
- 文件：`yolo/embedded_model.*`

特点：

- 模型是内嵌的，不依赖外部模型文件路径
- 基于 RKNN 运行
- 输出分割/检测结果
- 支持生成 JSON
- 可把检测结果叠加到图像上保存

### 8.3 结果缓存

`yolo_wrapper.cpp` 会缓存最近一次成功检测的结果，用于：

- 在 `DETECT` 中拿到 `objects` JSON
- 保证返回的 JSON 和当前响应图像属于同一帧

### 8.4 结果落盘

当 `YOLO_SAVE_IMAGES` 开启并且有检测结果时，会把带框结果图保存到：

- `/home/linaro/build/img`

## 9. 标定功能

### 9.1 主摄标定

- 文件：`camera_calibreation/mainCamera/main_camera_fisheye_calib.h`
- 文件：`camera_calibreation/mainCamera/main_camera_fisheye_calib.cpp`

主摄标定做的事情：

1. 从 NV12 帧中提取棋盘格
2. 执行鱼眼标定
3. 做质量闸门校验
   - RMS 必须满足要求
   - 内参/畸变/外参必须在合理范围
4. 成功后写出：
   - `calibration/results/session_时间戳/reallinkCV.bin`
   - EEPROM
   - `/home/linaro/reallinkCV.conf` 中的主摄外参

当前代码里，主摄标定明确要求质量闸门通过，且注释中写明使用了严格条件 `RMS < 1.0`。

### 9.2 XYoffset 标定

- 文件：`camera_calibreation/XYoffset.h`
- 文件：`camera_calibreation/XYoffset.cpp`

功能流程：

1. 平台移动到固定点
2. 固定下降到指定高度
3. 打开激光
4. 采集多帧并检测激光点
5. 计算理论位置与实际位置之间的像素偏移
6. 把 `cam0.dxPx / cam0.dyPx` 写入 `reallinkCV.conf`
7. 重建 overhead maps

它的作用是让 BEV 图像的 0 点和真实物理坐标对齐。

### 9.3 副摄标定

- 文件：`camera_calibreation/viceCamera/vice_camera_service.h`
- 文件：`camera_calibreation/viceCamera/vice_camera_service.cpp`

副摄标定是一个完整的服务类，负责：

1. 创建 session 目录
2. 控制机械移动到固定采样点
3. 采集副摄图像
4. 在每个位置做激光测高
5. 用 ChArUco 角点做相机标定
6. 汇总每个采样点的姿态与高度信息

代码中 `fixed_coordinates_` 定义了 16 个固定采样点，因此这条链路本质上是一套“多点采样 + 相机求参”的流程。

### 9.4 总高测量

- 文件：`camera_calibreation/totalHigh.h`
- 文件：`camera_calibreation/totalHigh.cpp`

功能流程：

1. 归位
2. Z 轴按步长下降
3. 通过激光传感器获得距离
4. 计算 `totalHigh`
5. 写入 `/home/linaro/reallinkCV.conf`
6. 同时把结果写进 `calibration/results/reallinkCV.bin`

当前实现里，`CalibData.distCoeffs[4]` 被拿来额外保存 `totalHigh`。

### 9.5 底层标定支持目录

#### `calib/`

这是标定算法支持目录，包含：

- `ChessboardDetector.*`
- `charuco_detector.*`
- `calibinit.*`
- `cbdetect/`

主要承担：

- 棋盘格角点检测
- ChArUco 检测
- 标定初始化与几何算法

#### `calib/camToolKit/`

这是偏设备/固件的标定工具集，包含：

- EEPROM 读写
- Sonix 相机工具
- `CalibData` 结构定义

主要用于把标定结果写入设备侧固件存储。

## 10. Klipper / Moonraker 联动功能

### 10.1 管理器

- 文件：`camera_calibreation/klipper/klipper_manager.h`
- 文件：`camera_calibreation/klipper/klipper_manager.cpp`

这是整个项目和运动控制系统交互的统一入口。

主要能力：

- 初始化连接
- `ensureHomed()` / `forceHome()`
- 发送 G-code
- 查询激光距离
- 通用 Z 轴下探探测
- 查询焦距
- 设置补光灯亮度
- 开关激光

多个功能模块都依赖它：

- `DETECT`
- `thickness`
- `CALIB`
- `XYoffset`
- `totalHigh`
- `ViceCameraService`

### 10.2 focal 查询

- 文件：`camera_calibreation/focalabfocal.h`

## 13. 当前实现中的几个注意点

1. `DETECT` 依赖 BEV latest frame，而 BEV 帧只有在 BEV 流实际处理时才会刷新，所以检测功能与 BEV 推流状态存在耦合。
2. 命令服务当前是同步连接处理模型，不适合大量并发客户端同时访问。
3. 原图推流优先使用 DMA-BUF 零拷贝路径，非 DMA-BUF 原图会被直接丢弃。
4. BEV 推流当前也要求 DMA-BUF 输出，否则会丢帧。
5. `sendErrorResponse()` 当前实际只返回 `{"status":"FAILED"}`，并不会把 `error_code` 和详细错误文本发给客户端。
6. `QUIT` 只出现在错误提示文本中，代码里没有实际 handler。

## 14. 一句话总结

`t3/reset/src` 本质上是一套“主摄采集 + 双路 RTSP 推流 + BEV 俯视图 + YOLO 检测 + Klipper 联动 + 多阶段相机标定”的嵌入式视觉服务系统，其中在线推流、在线检测、离线标定和配置持久化都已经打通，并通过统一命令端口对外暴露。
